## Pasteable Discussion / PR Body

This proposes an optional example showing how a PydanticAI app can route one
high-risk tool through a compile-time Heat boundary.

The example does not change PydanticAI core and does not add Heat as a package
dependency for normal users. It keeps the existing PydanticAI shape:
`Agent`, `RunContext`, dependency injection, and `@agent.tool`. The only new
line in the tool implementation is a boundary call before the side effect:

```python
allowed, reason = heat_boundary.check_export_case_file(path=path, content=content)
if not allowed:
    return "blocked by Heat boundary: " + reason
```

The value is that the boundary fails closed for cases that are easy to miss
with Python-only conventions:

- model-controlled file path reaches `write_file`
- a future helper bypasses a Python guard function
- model-controlled webhook URL/body reaches `http_post`

The committed proof is generated by `heatc`; unsafe flows are refused before
the unsafe binary is emitted, while repaired flows still build.

I am proposing this as an example/cookbook entry first. If this direction is
interesting, a follow-up could explore a tiny reusable tool-executor adapter.

## Maintainer-Facing Summary

This adds a small optional example showing how a PydanticAI app can route one
high-risk tool through a compile-time Heat boundary.

It does not add Heat to PydanticAI core. It does not change agent execution.
It keeps the existing `Agent` / `RunContext` / `@agent.tool` pattern and places
the boundary at the same point teams already make external-action decisions:
inside the tool implementation.

## Why It Belongs As An Example

PydanticAI already moves structure, dependency injection, and output validation
earlier. Heat covers a different failure class: unsafe provenance reaching an
egress sink even when Python shape validation succeeds.

Python can express this as a guard function, decorator, approval callback, or
review convention. Those are useful, but they only protect call paths that
remember to use them. In the Heat boundary, the sink requires `@path_safe`;
`@user_input` cannot reach it. A missed helper function fails the build.

## What The Example Shows

- Before: model-shaped tool args reach filesystem egress.
- Missed helper: a future helper writes directly and bypasses a Python guard
  convention.
- Webhook: model-shaped URL/body args reach network egress.
- Boundary: the tool implementation calls one adapter before side effects.
- Proof: `heatc` refuses the unsafe flows with `NL-OBL-001` / `NL-0500`.
- Repair: a laundered `@path_safe` flow builds and runs.
- PydanticAI path: `TestModel` can call the registered `@agent.tool` without
  API keys, and the tool returns the Heat refusal instead of writing the file.

## Intended Scope

Keep this as an optional example/cookbook entry first. If maintainers find it
useful, a later PR could explore a tiny reusable tool-executor adapter.
